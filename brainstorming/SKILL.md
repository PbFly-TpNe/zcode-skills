# Brainstorming（方案共创）

目的：在写任何代码之前，把"想要什么"彻底弄清楚，最终产出一份开发者无需再问人就能照做的设计文档。

## 流程（八步）

### 1. 评估已知信息
- 回复前先判断：需求是否完整明确。完全明确（如"把图标改成蓝色"）→ 直接做，做完汇报。
- 有关键点不明确 → 进入对话。
- **先查再问**：在已有项目里，先读完相关代码和文档，绝不问材料里已有答案的问题。

### 2. 开场
- 用户给了详细需求：用自己的话复述（做什么、为谁、为什么，约 200 字），指出被忽略的约束，最后问一个最大的开放问题。
- 没有明确需求：用用户的语言问一个开放问题，并说明答案会影响什么。
- 用户没有主动要求头脑风暴时，附一句"或者你想让我直接开干也行"。

### 3. 对话（核心）
- **每条消息只以一个问题结尾**——一句话，不给选项列表，不解释流程。
- 优先开放问题；顺着上一轮回答追问（苏格拉底式，如"中途加入的人有投票权吗？"）。
- 需要覆盖的方面（自然穿插，不当清单念）：这是什么、特别在哪；为什么现在做、成功是什么样；目标/非目标/反目标；已有的类似实现；现状；用户特别在意的细节。
- 尽早弄清哪些"怎么实现"的选择用户想自己拍板；你替他做的决定要在文档里标为你的决定。
- 主动提出可以深入调研（读代码库/文件/上网查），由用户决定。
- 可提供 spike（一次性验证性小构建）选项：spike 少写测试、不进正常流程。

### 4. 给出方案选项
理解需求后，单独发一条消息列出 2-3 个真实可行的方案（砍掉弱的），每个附权衡，推荐一个并说明理由，让用户选。若只有一条合理路径，直接说明为什么。

### 5. 复述确认
- 每弄清一部分，就用 200-300 字复述；提问与复述交替直到覆盖完毕。
- 用户说过的用原话；你补充的标为"提议"并给理由。
- 每段结尾问"哪里不对/还缺什么"。
- 描述视觉内容前，先提出用可视化展示（ZCode visualize / HTML mockup），等用户回应；被拒绝就保持纯文本，不再提。

### 6. 评估工作量
| 规模 | 产出 |
|---|---|
| 小改动 | 简短设计记录：把讨论结果写下来即可 |
| 完整项目 | 完整书面设计 |

用户可覆盖。中途范围变大 → 停下来升级档次。多个独立项目 → 商定顺序，一次只头脑风暴一个。

### 7. 写成设计文档
写一份"开发者不再问人就能照做"的文档，包含：意图与原因；目标/非目标/反目标；约束；候选方案（含权衡与用户的选择）；已定决策；留给实现者的部分。
- 保存到 `docs/specs/YYYY-MM-DD-<主题>-design.md`（仓库内则提交入库；否则询问用户）。
- **Builder check（项目内）**：用 Agent 工具派一个全新子代理通读文档并提问，把问题分三堆：①文档已回答的→补进文档；②小事→自己定并标注为你的决定；③必须用户拍板的→一次性带回（重要的在前）。只做一轮。

### 8. 批准门槛
**设计文档未经用户批准，一行代码都不写**——包括脚手架、装依赖、建项目。例外：用户明确要求跳过提问，或已批准的 spike（保留 spike 产物视同新请求，需重新批准）。

批准后 → 使用 **writing-plans** skill 产出实施计划。

## 红线清单
- 不要一上来就给选项菜单——先让用户描述
- 可以用默认值，但要说出口
- 没有单独发过"方案选项"消息之前，不要动笔写文档
- 不解释流程，只问你的问题
- 用户对想法说"不错"≠ 批准文档
- spike 的产物要转正 = 新请求，回到批准门槛
