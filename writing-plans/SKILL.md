# Writing Plans（实施计划）

读者画像：**不熟悉这个代码库的工程师**。计划里只写他推不出来的东西：确切的文件、名称、签名、规格值、测试。

开始时宣布"开始写计划"，完成后把计划保存到 `docs/plans/YYYY-MM-DD-<功能名>.md`（用户偏好优先）。

## 原则
- DRY、YAGNI、TDD、频繁提交、任务切小。
- 涉及多个子系统的 spec → 拆成多份计划，每份独立产出可运行的软件。

## 写法

1. **文件结构先行**：先画出要新建/修改哪些文件、各自职责，再定义任务；文件保持专注，遵循代码库既有模式。
2. **任务 = 最小的可独立测试、可被评审拦截的单位。**
3. **步骤 = 一个动作 + 一个可检查的结果**：写失败测试 → 运行确认失败 → 最小实现 → 运行确认通过 → 提交。

## 计划头（必须有）
- 目标、架构、技术栈、spec 路径
- **全局约束**：来自 spec 的精确数值/规则
- **复审重点**：列出 5 个最可能的失败模式，每个配一个"钉死测试"，放进对应任务

## 每个任务（必须有）
- 涉及的确切文件；消费/产出的接口
- 复选框步骤：失败测试代码 → 验证失败的命令 → 实现步骤（只在算法不确定时写细节，否则只写签名）→ 验证通过的命令 → 提交

## 步骤标准
每一步要无歧义——"实现者只能写出一种合理的东西"。计划比它描述的代码还长 = 流水账；出现"待定"行 = 失败。

## 自审（五查）
spec 覆盖完整？逐步骤扫一遍？类型/命名前后一致？复审重点都有着落？篇幅与 spec 相称？问题就地修复。

## 交接
计划写完后交给用户评审，并提供两种执行方式供选择：
- **子代理执行**：用 Agent 工具每个任务派一个全新子代理 + 评审（上下文干净，适合大计划）
- **本会话执行**：当前会话按计划顺序做，最后统一评审
