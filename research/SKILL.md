# Research（深度调研）

## 核心原则
- **多源**：重要结论绝不只靠单一来源
- **交叉验证**：所有关键信息在独立来源间互证
- **必须引用**：每条结论都要有出处，禁止无来源断言
- **承认不确定**：来源冲突或薄弱时明确说出"不确定"
- **优先一手来源**：官方文档 > 博客 > 论坛问答 > AI 生成内容

## 工具选择（ZCode 环境）
| 工具 | 适用 | 局限 |
|---|---|---|
| WebSearch | 时效信息、广泛发现 | 可能过时、受 SEO 影响 |
| WebFetch | 读指定 URL、提取内容 | 需要知道 URL |
| browser-use（控制浏览器） | 交互式页面、需登录内容、复杂导航 | 慢、耗 token |
| MCP 文档服务器（若配置） | 库/框架官方文档 | 只覆盖已索引的库 |
| Grep/Glob/Read | 本地代码库调研 | 仅本地文件 |

## 五阶段流程

### 1. 界定范围
明确核心问题、深度要求（快速摘要 vs 深挖）、时效要求、什么算权威来源。方向不止一个时先问清用户。

### 2. 来源发现
- 用 3-5 种查询变体（专业说法 + 日常说法）
- 专门搜"[主题] 官方文档"、论文/研究报告
- 权威性判断：.gov/.edu 倾向可靠；项目官方文档对该项目就是权威；**维基百科是起点不是终点——顺它的引用找源头**；论坛回答看日期/票数/是否被采纳；警惕内容农场和 SEO 榜单文

### 3. 深度阅读
每个来源：取全文 → 提取关键论断（数据/日期/引语）→ 记录元信息（作者/日期/立场）→ 追它的引用 → 标记与其他来源的冲突。
分类策略：文档全读并记版本号；论文按摘要→结论→方法顺序；新闻先看日期和引用源；博客独立验证；论坛答案必须独立验证。

### 4. 交叉验证
- 每条重要结论找 **2+ 个互不引用的独立来源**
- 冲突处理：并列报告所有说法及引用；调查**为什么**冲突（版本/立场/时间）；有明确更权威的一方就注明；**绝不悄悄挑一个说法**

### 5. 综合成报告
固定结构：
1. **核心发现**：编号列表，每条含事实、引用编号、置信度
2. **冲突与不确定性**：分歧点及原因分析
3. **来源质量表**：编号/URL/类型/权威性/时效/备注
4. **缺口与局限**：没能验证什么、还需要查什么
5. **引用列表**：完整出处（标题、URL、访问日期、发布日期）

## 置信度标注
- **高**：3+ 个独立权威来源一致，无冲突
- **中**：2 个来源一致，或仅一个高权威来源；小冲突
- **低**：单一来源，或有显著冲突
- **不确定**：存在无法消解的重大分歧

每条结论必须显式标注——"我不确定"本身就是有效结论。

## 特殊场景
- **快速演变的主题（AI/行业动态）**：优先近 6 个月信息，查 changelog/发布说明，标注可能过时的内容
- **争议话题**：并列所有立场及最强论据，注明各方偏差，除非证据压倒性否则不站队
- **技术实现问题**：先查官方文档，找 GitHub 实例代码，注意版本差异
- **对比调研（X vs Y）**：对所有选项用同一套评价标准，警惕厂商 bias，说明各自优化方向

## 反模式（禁止）
单一来源；无引用断言；默认第一条搜索结果最好（SEO≠准确）；忽略冲突；用过时来源；直接信 AI 摘要（会幻觉，要追一手来源）；过早收工（调研到边际收益递减为止）。

## 完成标准
核心问题都有带引用的回答；关键论断有 2+ 独立来源；冲突与不确定已标注；来源质量已评估；置信度已给出；缺口已记录。
